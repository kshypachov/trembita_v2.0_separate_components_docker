1. Вступ

Даний посібник призначено для Аудиторів транзакцій, які відповідають за верифікацію підписів повідомлень, якими обмінюється сервер безпеки на платформі Unified eXchange Platform (UXP).

Цей довідник описує як:

  • шукати та переглядати повідомлення успішного обміну сервера безпеки;

  • верифікувати підписи повідомлень;

  • завантажувати контейнери підписів;

  • завантажувати пов’язані з підписами сертифікати.

Сервер безпеки зберігає підписи лише успішно опрацьованих сервером повідомлень. Таким чином, сторінка Повідомлення на сервері безпеки не може використовуватися як джерело отримання інформації про усі отримані сервером повідомлення. Для перегляду усіх повідомлень, отриманих сервером (включно з помилковими повідомленнями з певних причин), має бути налаштовано збір даних операційного моніторингу сервера (описано у посібнику [UXP-UG-PMA]).

Роль Аудитора транзакцій є залежною від учасника системи UXP. Отже, Аудитор транзакцій може лише переглядати повідомлення, у яких клієнт або постачальник сервісу є учасником UXP, для якого аудитор має відповідні привілеї. Щоб переглянути свої ролі та привілеї на сервері, перейдіть у Мій профіль.

Цей посібник не описує роботу з сервером безпеки UXP, припускаючи, що ця робота доручена комусь іншому (оператору UXP). Тому зверніться до вашого оператора UXP за допомогою щодо:

  • керування користувачами;

  • моніторингу сервера;

  • системних журналів.

1.1. Сервер безпеки UXP

Головним призначенням сервера безпеки є посередництво у керуванні запитами з метою збереження їх доказової цінності.

Сервер безпеки під’єднано до відкритої мережі Інтернет з одного боку та до інформаційної системи у внутрішній мережі організації з іншого боку. В певному сенсі, сервер безпеки можна розглядати як спеціалізований програмний мережевий екран, який може здійснювати посередництво для SOAP та REST вебсервісів; отже його слід налаштовувати паралельно з мережевим екраном організації, який контролює інші протоколи.

Сервер безпеки оснащено функціональністю для забезпечення захисту обміну повідомленнями між клієнтом та постачальником сервісних послуг.

  • Повідомлення, що передаються через відкриту Інтернет мережу захищаються з допомогою цифрових підписів та шифрування.

  • Сервер безпеки постачальника сервісу контролює доступ до вхідних повідомлень, забезпечуючи доступ до даних лише тим користувачам, які підписали відповідну угоду з постачальником сервісу.

1.2. Концепція UXP

  • Екземпляр UXP окрема копія налаштованої інфраструктури системи UXP.

  • Керівний орган UXP організація, відповідальна за підтримку екземпляра UXP.

  • Учасник UXP фізична або юридична особа, що приєдналася до системи UXP для надання та/або отримання сервісів.

  • Підсистема представляє частину інформаційної системи учасника UXP. Для можливості використовувати чи надавати сервіси UXP, учасники UXP повинні вказувати частини своїх інформаційних систем як підсистеми.
    Підсистеми є автономними у частині надання та використання сервісів UXP.

    • Права доступу для підсистем учасників UXP незалежні — права, надані одній підсистемі, не впливають на права доступу для інших підсистем учасника.

    • Сервіси, що надаються підсистемою є незалежними від сервісів, що надаються іншими підсистемами учасника.

      Учасник UXP може пов’язувати кілька різних підсистем з одним сервером безпеки, а також одна підсистема може бути пов’язана з кількома серверами безпеки.

  • Ідентифікатор учасника - унікальний ідентифікатор учасника системи UXP. Такий ідентифікатор складається з трьох частин: ідентифікатора екземпляра, класу учасника і коду учасника. Приклад ідентифікатора учасника: EE/GOV/12345678.

  • Ідентифікатор екземпляра - унікальний код, визначений для екземпляра UXP. Наприклад, кодом для естонського екземпляра розробки буде EE-DEV, а кодом для промислового екземпляра буде EE.

  • Клас учасника - групування учасників UXP із подібними властивостями у спільну сутність. Наприклад, державні органи групуються як клас учасників GOV, а приватні організації групуються як клас учасників COM.

  • Код учасника - пов’язується з певним учасником UXP і є унікальним в межах класу учасників. Код учасника залишається незмінним протягом усього періоду діяльності учасника UXP. Наприклад, кодом учасників для організацій і державних установ в Естонії є код державної реєстрації підприємств.

  • Код підсистеми - додається до ідентифікатора учасника для розрізнення окремих підсистем учасника.

  • Сервер реєстрації - компонент системи UXP, яким керує керівний орган, що виступає реєстром інформації, необхідної для роботи екземпляра UXP. Сервер реєстрації UXP поширює цю інформацію на сервери безпеки у формі глобальної конфігурації.

  • Сервер безпеки - компонент системи UXP, який з’єднує підсистему учасника UXP із інфраструктурою UXP.

  • Власник Сервера безпеки - учасник системи UXP, юридично відповідальний за певний сервер безпеки.

  • Клієнт Сервера безпеки - підсистема, зареєстрована на сервері безпеки. Реєстрацію має бути погоджено Керівним органом і підтверджено на сервері реєстрації.

  • Глобальна конфігурація - файл, що містить інформацію, необхідну для роботи сервера безпеки. Сервери безпеки періодично завантажують глобальну конфігурацію з сервера реєстрації. Приклади інформації у глобальній конфігурації:

    • учасники UXP та їх підсистеми;

    • зареєстровані сервери безпеки;

    • зареєстровані клієнти серверів безпеки;

    • зареєстровані сертифікати автентифікації;

    • глобальні групи;

    • налаштування системи UXP;

    • адреси та відкриті ключі OCSP сервісів (якщо раніше не надані через сертифікати доповнення 'Authority Information Access');

    • адреси та відкриті ключі підтверджених постачальників сертифікаційних послуг;

    • відкриті ключі проміжних центрів сертифікації;

    • адреси та відкриті ключі підтверджених постачальників послуг фіксації позначок часу.

  • Глобальна група - група прав доступу, що керується на рівні сервера реєстрації. Усі підсистеми у глобальній групі мають права доступу, визначені для цієї групи.

  • Локальна група - група прав доступу, що керується на рівні клієнта сервера безпеки.

  • Уповноважений з надання позначок часу (TSA) - постачальник сервісу, який надає фіксовані позначки часу.

  • Сервіси позначок часу - сервіси, що надаються TSA для забезпечення збереження доказових атрибутів повідомлень, якими обмінюються у системі UXP.

  • Позначка часу - дата та час з підписом, надані TSA для доказу, що повідомлення існувало у певний час.

  • Центр сертифікації (CA) - постачальник сервісу сертифікації, який надає цифрові сертифікати.

  • Сервіси сертифікації - сервіси, що надаються CA учасникам системи UXP, для забезпечення їх цифровими сертифікатами, необхідними для підтвердження права власності на відкритий ключ.

  • OCSP - Online Certificate Status Protocol (протокол отримання статусу цифрового сертифіката). OCSP-сервери - це сервери під керівництвом центрів сертифікації, через які опрацьовуються запити на перевірку чинності сертифікатів.

  • Ключі UXP - криптографічні ключі, що використовуються у системі UXP. Зокрема, у системі UXP використовуються пари з відкритого і приватного ключів.
    Ключ UXP може бути:

    • ключем підпису, що використовується серверами безпеки для цифрового підписання повідомлень, або

    • ключем автентифікації, що використовується серверами безпеки для встановлення захищених каналів зв’язку.

  • Сертифікати UXP - сертифікати, які видаються постачальниками сервісів сертифікації, затвердженими Керівним органом UXP.

  • Криптографічний пристрій - зовнішній механізм захисту криптографічних ключів для сервера безпеки, які сервер безпеки використовує для підписання повідомлень. Прикладами криптографічних пристроїв є апаратні модулі захисту (HSM) та USB токени.

  • Токен - сховище для захисту криптографічних ключів, які використовує сервер безпеки. Сервер безпеки має два типи токенів:

    • програмний токен — токен, що використовує вбудоване програмне забезпечення сервера безпеки,

    • апаратний токен — токен на криптографічному пристрої.

  • Сервіси UXP - сервіси, що надаються через інфраструктуру системи UXP.

  • Повідомлення UXP - однонаправлений обмін даними між клієнтом та постачальником сервісу в середовищі екземпляра системи UXP. Залежно від джерела походження, повідомленнями можуть бути запити або відповіді на них. Повідомлення UXP мають формуватися відповідно до Протоколу повідомлень UXP ([UXP-PR-MESS]), а створюються вони інформаційними системами учасників UXP.

  • Клієнт сервісу - підсистема учасника UXP, яка надсилає повідомлення із запитами.

  • Постачальник сервісу - підсистема учасника UXP, яка надсилає клієнту сервісу повідомлення з відповіддю на його повідомлення із запитом.

  • Контейнер підпису - файл, який містить підписане повідомлення UXP, цифровий підпис, позначку часу та відповідні сертифікати.

  • Транзакція - комбінація з повідомлення із запитом та відповідного йому повідомлення із відповіддю.

    • Ідентифікатор транзакції - ідентифікатор для транзакції, який визначає сервер безпеки клієнта сервісу під час опрацювання повідомлення із запитом від інформаційної системи. Ідентифікатор транзакції генерується сервером безпеки автоматично і містить унікальне значення для кожного повідомлення, опрацьованого на сервері безпеки.
      Ідентифікатор транзакції може використовуватися для однозначної ідентифікації повідомлення UXP серед інших.

  • Запит - повідомлення із запитом, ініційоване клієнтом сервісу.

    • Ідентифікатор запиту - ідентифікатор транзакції, який є частиною заголовку повідомлення (id у SOAP заголовках ([UXP-PR-MESS]) та Uxp-Queryid у HTTP заголовках). Ідентифікатор запиту визначається інформаційною системою клієнта сервісу.

  • Заголовки UXP - заголовки повідомлень, що є специфічними для системи UXP і використовуються для включення в повідомлення UXP специфічних метаданих.

    • Для SOAP сервісів, заголовки можна переглянути в [UXP-PR-MESS].

    • Для REST сервісів, заголовками UXP є:

      • Uxp-Client

      • Uxp-Service

      • Uxp-Queryid

      • Uxp-Transaction-Id

      • Uxp-Userid

      • Uxp-Consent-Ref

      • Uxp-Issue

2. Керування власним обліковим записом

2.1. Перегляд своїх ролей

Щоб переглянути, які ролі має ваш обліковий запис, виконайте наступні кроки:

  1. Наведіть курсор миші на ваше ім’я користувача у верхньому правому куті вікна.

  2. Натисніть на Мій профіль. У таблиці, що відкриється, ви зможете побачити, які ролі для яких учасників ви маєте.

Якщо ви не бачите ваших учасників сервера безпеки, або ви не маєте бажаних ролей, зверніться до вашого адміністратора сервера.

2.2. Зміна паролю

Щоб змінити пароль для вашого облікового запису, виконайте наступні кроки:

  1. Наведіть курсор миші на ваше ім’я користувача у верхньому правому куті вікна.

  2. Натисніть на Змінити пароль.

  3. Введіть старий пароль, а потім новий і натисніть Зберегти.

Щойно ви зміните пароль, вашу робочу сесію буде припинено і ви повинні будете авторизуватися повторно.

2.3. Скидання забутого паролю

Якщо ви забулися свій пароль, зверніться до вашого адміністратора сервера і попросіть його скинути ваш пароль.

3. Повідомлення

Повідомлення UXP є односпрямованим обміном даними між клієнтом та постачальником сервісу в межах екземпляра системи UXP. Залежно від походження, повідомлення може бути запитом або відповіддю. Кожне повідомлення UXP має цифровий підпис відправника.

Разом, повідомлення запиту і відповіді складають транзакцію. Транзакція має двох учасників:

  • Клієнт сервісу — підсистема учасника UXP, яка надіслала повідомлення із запитом.

  • Постачальник сервісу — підсистема учасника UXP, яка надіслала повідомлення із відповіддю клієнту сервісу у відповідь на його повідомлення із запитом.

Контейнер підпису є файлом, що містить підписане повідомлення UXP, цифровий підпис, позначку часу та пов’язані сертифікати.

3.1. Пошук повідомлень

Права доступу: Аудитор транзакцій

Для пошуку повідомлень можна використовувати Простий пошук або Розширений пошук. Простий пошук призначений для швидких пошукових запитів, в той час як Розширений пошук може запропонувати більш тонкі налаштування.

Щоб знайти повідомлення, виконайте наступні кроки на сторінці Повідомлення:

  1. Відкрийте Простий пошук або Розширений пошук.

  2. Заповніть бажані поля.

  3. Натисніть Пошук.
    В результаті буде показано список повідомлень, які відповідають заданим критеріям пошуку.

Щоб очистити поточний заданий фільтр пошуку, натисніть Очистити фільтри.

Щоб оновити список повідомлень, натисніть Пошук або кнопку оновлення.

Повідомлення не оновлюються у реальному часі. Якщо ви очікуєте нових повідомлень, періодично оновлюйте список самостійно.

3.1.1. Простий пошук

Простий пошук дозволяє виконувати пошук за такими полями:

  • Поля клієнта:

    • Назва;

    • Підсистема;

3.2. Верифікація підпису повідомлення

Права доступу: Аудитор транзакцій

Щоб верифікувати підпис повідомлення, відкрийте сторінку Повідомлення. Знайдіть повідомлення і натисніть Подробиці. Сервер спробує верифікувати підпис та покаже результат.

3.2.1. Стани повідомлень

Стани повідомлень показують чи може бути підпис верифікованим.

Повідомлення може мати один з таких чотирьох станів:

  • Очікування позначки часу – Контейнер підпису очікує на отримання позначки часу. Верифікувати підпис або завантажити контейнер підпису неможливо.

  • Отримано позначку часу – Контейнер підпису має позначку часу, але ще не заархівований. Можна переглянути результат верифікації та завантажити контейнер підпису.

  • Заархівовано – Контейнер підпису заархівовано, верифікувати та завантажити контейнер підпису можна лише якщо контейнер доступний на архівному носії даних. Якщо контейнер доступий, можна переглянути усі його подробиці, включно з даними підпису.

  • Відсутні дані – Контейнер підпису відсутній (наприклад, дані підпису було втрачено через збій електроживлення). Верифікувати підпис або завантажити контейнер підпису неможливо.

3.2.2. Подробиці повідомлення та результат верифікації

Подробиці повідомлення:

  • Тип повідомлення;

  • Ідентифікатор транзакції;

  • Ідентифікатор запиту;

  • Ідентифікатор користувача;

  • Опрацьовано (час, коли сервер безпеки опрацював вхідне повідомлення);

  • Клієнт сервісу;

  • Постачальник сервісу;

  • Код сервісу;

  • Версія сервісу;

  • Версія протоколу.

Підпис та результат його верифікації:

  • Чи підпис є чинним;

    • Якщо сервер безпеки не може верифікувати підпис, причина цього;

      Якщо верифікація підпису невдала, підпис насправді може бути й чинним, але у сервера безпеки може бути недостатньо інформації, щоб його верифікувати.

  • Чи є підпис кваліфікованим;

    • Підпис є кваліфікованим, якщо сертифікат підпису є кваліфікованим і сам підпис чинний.

  • Час підпису.

Якщо на сервері безпеки ввімкнено параметр перевірки кваліфікованих підписів, сервер буде відхиляти повідомлення з некваліфікованими підписами — такі повідомлення сервер не передає далі і не зберігає. Отже, якщо вимога кваліфікованого підпису ввімкнена, лише кваліфіковані підписи записуються на сервері та відображаються у таблиці Повідомлення.

  • Сертифікат підпису:

    • Чи є чинним сертифікат;

      • Якщо сертифікат не чинний, причина цього;

    • Чи є сертифікат кваліфікованим;

      • Сертифікат підпису є кваліфікованим, якщо центр сертифікації (CA), який його видав, підтвердив, що сертифікат видано відповідно до стандартів контролю якості та для приватного ключа на криптографічному пристрої (доповнення qcStatements у сертифікаті включає атрибути qcCompliance та qcSscd). Крім того, має бути кваліфікованим весь ланцюжок сертифіката.

    • Серійний номер;

    • Ім’я об’єкту;

    • Видавець;

    • Видано;

    • Термін дії до;

    • Відбиток (SHA-1).

OCSP-відповідь для сертифіката підпису:

  • Чи є OCSP-відповідь чинною;

    • Якщо OCSP-відповідь не чинна, причина цього;

  • OCSP-відповідь;

  • Створено.

  • Сертифікат сервера OCSP:

    • Чи є сертифікат чинним;

      • Якщо сертифікат не чинний, причина цього;

    • Серійний номер;

    • Ім’я об’єкту;

    • Видавець;

    • Видано;

    • Термін дії до;

    • Відбиток (SHA-1).

Позначка часу:

  • Чи є позначка часу чинною;

    • Якщо позначка часу не чинна, причина цього;

  • Значення.

  • Сертифікат TSA:

    • Чи є сертифікат чинним;

      • Якщо сертифікат не чинний, причина цього;

    • Серійний номер;

    • Ім’я об’єкту;

    • Видавець;

    • Видано;

    • Термін дії до;

    • Відбиток (SHA-1).

Сервер OCSP та сертифікати TSA стають не чинними, якщо керівний орган видаляє їх сертифікати зі списку підтверджених серверів OCSP і TSA на сервері реєстрації.

3.3. Завантаження контейнера підпису

Права доступу: Аудитор транзакцій

Щойно підпис отримує позначку часу, контейнер підпису стає доступним для завантаження.

Щоб завантажити контейнер підпису, можна:

  1. Перейти на сторінку Повідомлення.

  2. Знайти потрібне повідомлення.

  3. Натиснути Завантажити.

або

  1. Відкрити сторінку подробиць повідомлення Дані повідомлення.

  2. Натиснути Завантажити.

У випадку із заархівованими підписами, сервер безпеки може повернути контейнер підпису, лише якщо контейнер ще доступний на сервері зберігання чи в архівному сховищі.

3.4. Завантаження сертифікатів

Права доступу: Аудитор транзакцій

Щоб завантажити пов’язаний з підписом сертифікат, перейдіть у повідомленні на сторінку Дані повідомлення і оберіть бажаний для завантаження сертифікат.

Можуть бути завантаженими такі три типи сертифікатів:

  • Сертифікат підпису для ключа підпису, використаного при підписанні повідомлення відправником повідомлення.

  • Сертифікат OCSP сервера для OCSP сервера, який надав OCSP-відповідь для сертифіката підпису.

  • Сертифікат TSA для сервісу позначок часу, який надав повідомленню позначку часу.
